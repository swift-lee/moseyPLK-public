# 开发与验证流程

所有命令从项目根目录执行。开始时检查 `git status --short`，阅读 [当前状态](current-state.md) 和 [公开范围](publication.md)，保留现有修改。

## 主机工作

1. 依据代码确认行为与依赖，保持 `release.json` 为共同版本源。
2. 按 [测试说明](testing.md) 运行相关检查；默认检查使用主机夹具，不读取真实 APK 或旧安装包。
3. 外部输入、工具缓存、生成配置和输出统一放入 `moseyPLK-assets/`。缺少输入就报告缺口，不自动连接手机补齐。
4. 新增公开文件先审查来源、许可和隐私，再更新 `publication-files.json`。所有源码归档复用同一清单。
5. 收尾运行 `python3 scripts/check_harness.py` 和 `git diff --check`，记录实际通过、失败、跳过及限制。实现变化同步本目录说明。

文档变更只需链接与差异检查。源码变更运行对应测试；构建依赖未变化时无需重复下载工具或刷新锁文件。客户端只使用既有签名，旧基线打包入口保持明确停止。

## 手机只读调查

只有用户要求手机检查且通道已获授权时才进行。先审阅将执行的脚本与命令，确认唯一目标设备、型号、用户和启动身份。通过已有 ADB/root 通道将脚本从 stdin 输入，输出仅保存到主机的忽略资产目录。

可审阅的采集入口为 `scripts/collect-startup-readonly.sh`、`collect-registration-readonly.sh`、`collect-client-readonly.sh` 和 `collect-gms-startup-readonly.sh`。根据问题选择所需范围，不自动运行全部采集器。启动期日志需要在用户操作前开始有界监听，确认预检结果并记录实际结束；缺失日志保留为证据缺口。

助手不安装、授权、强停、启动、停止、重启、修改设置或数据库，不在手机暂存脚本，也不清日志。模块的 service、Action、状态发布及 `control.sh start/stop/restart` 会写入状态或启动进程，不能代替只读采集。用户完成必要动作并给出结果后，再继续核对。

## 判断与交接

关联同一启动、用户、包版本和 PID/starttime，分别核对文件、进程、Binder、hook、自然调用、绑定、发现及完成收发。`Running`、缓存命中和配置值为 true 各自只能说明对应层。

GMS 更新后的失效先核对完整版本、更新时间、客户端变体和解析/拒绝/hook 事件，再按证据调查绑定与无线层。用户反馈、原始日志与主机结果分别标注。公开文档只留脱敏方法和结论，不复制实际账号、设备标识、数据库或日志。
